# WorkBuddy 使用与真实 MCP 验证记录

验证日期：2026-10-09。项目由 **GPT/Codex 辅助开发，主要用于 WorkBuddy**。本页记录使用验收，不作为 WorkBuddy 开发作品或专项开发材料。

证据为作者提供的两份 WorkBuddy 导出和作者在提交材料时的成功下单反馈。两份导出按原顺序合并为 [完整脱敏使用记录](workbuddy-usage-records.md)，保留全部 5 轮用户对话及 94 次工具调用段落；失败、修正和原回复均保留。公开记录替换链接、用户名、地址、坐标、手机号、券码、凭据及追踪标识，不替换商品名称、配置、金额和调用结果。

## 两人 70 元场景

会话时间为 16:39:49–16:50:00。需求：两人都吃牛肉汉堡、都喝有糖可乐、至少一份薯条，A 饭量较大，B 想要 1+1 吉士汉堡并去洋葱。

记录确认 `/mcd-optimize` 加载、安装目录资料读取和 Node.js **v22.22.2** 执行；WorkBuddy 查询真实门店、菜单与套餐详情，将条件转换为本地输入，运行候选搜索，再将真实计价结果回填。调试中修改的是临时输入构建脚本和搜索参数，不意味着重新开发本 Skill。

| 组合 | 官方 `data.price`（分） | 金额 |
|---|---|---|
| 巨无霸三件套 + 精选超值随心配 + 人气经典随心配 | 6580 | 65.80 元 |
| 中薯条 + 精选超值随心配 + 人气经典随心配 | 4330 | 43.30 元 |
| 巨无霸三件套 + 人气经典随心配 | 5190 | 51.90 元 |
| 双层吉士汉堡中套餐 + 人气经典随心配 | 4890 | 48.90 元 |

当时门店为郑州瀚海海尚餐厅，到店场景；随心配按实际选项配置可乐，B 的双层吉士汉堡按去洋葱要求传入特调。价格是当时的服务返回，不是长期售价、付款金额或全菜单最优证明；不同商品组合的差额不称为同款节省额。

逐条统计工具调用 40–55：共 **16 次 `calculate-price`**，其中 **13 次成功**，含 1 次单独套餐配置校验和 12 次候选计价；调用 46–48 共 **3 次参数 Schema 校验失败**。原最终回复“12 次全部成功、0 失败”只反映其候选口径，不能代表整轮。默认 12 次调用预算未约束所有 Agent 直接调用，是待改进项。

本轮没有营养需求，也没有真实营养查询。记录包含输入调整和脚本调试，不能声称无需适配即可一次运行成功。

## 百人 100 元场景

会话时间为 16:59:19–17:13:44，共 4 轮用户反馈。WorkBuddy 调用真实门店、菜单、套餐详情、账户券/门店券及计价工具；当时账户和门店无可用券。四次计价分别返回 9900、9550、10000、29000 分。

| 组合 | 官方核价 | 用途 |
|---|---|---|
| 中薯条 ×6 + 苹果片 ×1 + 圆筒冰淇淋 ×1 | 99.00 元 | 首轮采购方案 |
| 中薯条 ×5 + 麦辣鸡腿汉堡 ×1 | 95.50 元 | 首轮备选 |
| 中薯条 ×6 + 小杯玉米杯 ×1 | 100.00 元 | 用户反馈后调整采购方案 |
| 麦乐鸡 5 块 ×20 盒 | 290.00 元 | 超出原预算、明确列为备选 |

这是一项极端预算下的对话与分配规则使用案例。当前本地引擎最多 8 人，记录明确改用 WorkBuddy 对话推理，没有用引擎求解 100 人。薯条根数及玉米粒数未由官方数据或实物清点证明，不能把聊天中的“人人 3 根”“数学上限”等断言写成已验证性能。均分时必须以实际清点量为准；人均 1 元不代表足量餐食或饱腹保证。
